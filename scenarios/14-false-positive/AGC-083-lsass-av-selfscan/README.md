## Alert / Trigger

In production SOC environments, Sysmon Event ID 10 (ProcessAccess) fires when any process accesses `lsass.exe` memory. Windows Defender's scan engine (`MsMpEng.exe`) routinely accesses LSASS during QuickScan and real-time protection operations, producing identical EID 10 alerts to those generated by credential dumping tools (Mimikatz, procdump, etc.). This is one of the highest-noise alert types in enterprise SOC operations.

**Lab constraint**: Sysmon EID 10 (ProcessAccess) is **disabled** in the SwiftOnSecurity configuration deployed on COMPROMISED-HOST-01. The investigation uses Defender operational logs and process/signature verification as alternative evidence.

## Simulation Summary

Triggered an on-demand Windows Defender QuickScan (`Start-MpScan -ScanType QuickScan`) on COMPROMISED-HOST-01. The scan completed in 10 seconds. Verified that `MsMpEng.exe` (PID 3220) is the Defender engine process and confirmed its Microsoft digital signature. In a production environment with EID 10 enabled, this scan would generate ProcessAccess events targeting `lsass.exe` with `SourceImage: MsMpEng.exe`.

**Execution window**: 00:42:09 - 00:42:19 UTC on COMPROMISED-HOST-01

**Process verification:**

The executable is validly signed by Microsoft with a current production certificate. This is the critical discriminating factor: a credential dumping tool masquerading as `MsMpEng.exe` would either lack a signature, have an invalid signature, or be signed by a different entity.

### Step 4: Sysmon EID 10 Detection Gap (Lab Constraint)

```
Sysmon EID 10 (ProcessAccess) events found: 0
```

Sysmon EID 10 is **disabled** in the SwiftOnSecurity configuration on this endpoint. In production, this event would show:

- `SourceImage`: `C:\ProgramData\Microsoft\Windows Defender\Platform\4.18.26080.3-0\MsMpEng.exe`
- `TargetImage`: `C:\Windows\System32\lsass.exe`
- `GrantedAccess`: `0x1410` or `0x1FFFFF` (depending on scan depth)

The absence of EID 10 does not affect the verdict -- the Defender operational logs independently confirm the scan activity, and the process signature verification confirms the identity of the accessing process.

### Step 5: LSASS Process Confirmation

```
lsass.exe running: PID 816
RunAsPPL: Enabled (Windows 11 default)
```

LSASS Protected Process Light (PPL) is active, which restricts access to lsass.exe from non-protected processes. MsMpEng.exe runs as a protected process and is permitted to access LSASS during scan operations.

## Discriminating Evidence (Benign vs Malicious)

| Factor | AGC-083 (Benign) | AGC-031 (Malicious) |
|--------|-------------------|---------------------|
| **SourceImage** | `MsMpEng.exe` (Defender engine) | Unknown binary, procdump, mimikatz, or renamed tool |
| **Digital signature** | Valid, Microsoft-signed (Windows Production PCA 2023) | Unsigned, invalid, or non-Microsoft signer |
| **Process path** | `C:\ProgramData\Microsoft\Windows Defender\Platform\` | Unusual path (Temp, Downloads, user profile) |
| **Scan correlation** | Defender EID 1000/1001 confirm active scan window | No scan activity in Defender logs |
| **GrantedAccess** | Standard scan access mask | Credential-dump access mask (0x1010, 0x1FFFFF) |
| **Process protection** | Runs as protected process (PPL-compatible) | Typically not a protected process |

**Signature verification is the strongest discriminator**. Process names can be spoofed (an attacker can rename a binary to `MsMpEng.exe`), but a valid Microsoft digital signature cannot be forged. If signature verification is not possible in a given investigation, confidence should be downgraded to Medium and the constraint documented explicitly.

## Conclusion

**Verdict: False Positive / Benign** -- The LSASS access is caused by Windows Defender's scan engine (`MsMpEng.exe`), which is validly signed by Microsoft and correlated with a confirmed QuickScan operation (Defender EID 1000/1001). This is routine AV behavior and does not represent credential access.

**Lab constraint**: Sysmon EID 10 (ProcessAccess) is disabled in the SwiftOnSecurity configuration. In production, this event would provide the direct `SourceImage`/`TargetImage`/`GrantedAccess` fields. The verdict is supported by alternative evidence: Defender operational logs confirming scan activity, process identity verification, and digital signature validation.

**Recommendation**: Close as Benign. Add the `MsMpEng.exe` signature + standard scan access mask pattern to the detection-tuning allowlist for LSASS access alerts. **Critical**: the allowlist condition must include signature verification, not just process name matching -- an allowlist that exempts any process named `MsMpEng.exe` regardless of signature creates a trivial bypass for attackers.

**Cross-reference**: The malicious twin of this scenario is **AGC-031**, where LSASS access comes from an unsigned or non-Microsoft binary with no corresponding Defender scan activity.
